DynamoDB-based state locking is deprecated and slated for removal in a future
Terraform minor release. S3 can now hold the lock itself, which removes a
table, an IAM policy and a bill line.

## Before you start

Confirm the Terraform version, because `use_lockfile` is not in older releases:

```bash
terraform version
aws s3api get-bucket-versioning --bucket your-state-bucket
```

Versioning matters more than it looks — the lock is an object, and you want its
history.

## Changing the backend

The old configuration names a table:

```hcl
terraform {
  backend "s3" {
    bucket         = "your-state-bucket"
    key            = "env/prod/terraform.tfstate"
    region         = "eu-west-1"
    dynamodb_table = "terraform-locks"
  }
}
```

The new one does not:

```hcl
terraform {
  backend "s3" {
    bucket       = "your-state-bucket"
    key          = "env/prod/terraform.tfstate"
    region       = "eu-west-1"
    use_lockfile = true
  }
}
```

Both can be set at once while migrating, which is the supported path when
several machines still run older Terraform versions.

## Verifying the lock

Hold a lock and look for the object:

```bash
aws s3api list-objects-v2 \
  --bucket your-state-bucket \
  --prefix env/prod/ \
  --query 'Contents[].Key'
```

## Cleaning up

Only delete the DynamoDB table once every consumer of the state has moved —
a stale `dynamodb_table` in someone's checkout will fail loudly, which is the
good outcome, but it will fail.
